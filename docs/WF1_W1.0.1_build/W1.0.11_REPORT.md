## 1. W1.0.11 - lead-per-campaign

**Business driver (Melisa):** campaign reach = leads created with a campaign name + `cold` label. Attaching a new campaign's touch to a person's OLD lead breaks the per-campaign reports. Live case: an Ai4-2026 touch landed on Person-1627ef6a's 2025 lead.

**Decision:** one lead PER CAMPAIGN per person; persons are NEVER duplicated; `campaign.name` is the logical key.

**What changed (11 nodes):**
1. **selectLead** in all 4 selectors (`Select Existing Lead`, `M5 Labels Compute`, `M6 Build`, `M7 Build`): picks the non-archived lead whose **Campaign field (`fields.lead_campaign` = 1cd81dfc...) == `campaign.name`** - never title parsing.
2. **Lead Create Gate**: create/existing conditions use the same `.some()` campaign-match, so a new-campaign touch on a person who already has an old-campaign lead CREATES a new lead (old untouched).
3. **Create Lead**: title convention `{campaign.id} - {campaign.name} - {full_name}` (numeric HeyReach campaign.id) + writes the lead Campaign field = `campaign.name`.
4. **Medium** (`fields.person_medium` = 961698945...): `LinkedIn` on Person Create + fill-if-empty in Person Patch Invited / M5 Person Patch Accepted / IF Rank gate.

**CONFIG additions:** `fields.lead_campaign` (lead "Campaign" custom field - created for this release) and `fields.person_medium` (person "Medium", pre-existing).

**Phases:**
| phase | result |

| A - scan | Read-only scan; documented the wrong-landing sample (Person-1627ef6a + others) -> `wf1-w111-phaseA-manual-fix.md` |

**Live L-A..L-D (proof the fix works):**
- L-A: old-campaign lead present -> a NEW-campaign event creates a SEPARATE lead; the reply patches ONLY the new campaign lead (`[cold, responded]`, event-truth, no `connected`); old lead untouched.
- L-B: 2nd reply -> same lead. L-C: replay -> gate `existing`, no dup. L-D: medium never overwrites a preset value, fills when empty.

## 3. Post-ship item 1 - rewrite the 22 wrong-landing leads (Nik+Melisa approved)

The 29 Ai4 touches that had landed on a pre-existing (older-campaign) lead resolved to **22 distinct leads** (1:1 with persons). All rewritten to the Ai4 convention:
- title -> `{campaign.id} - {campaign.name} - {person full name}` (Mario 512995 / Rune 513000)
- Campaign field -> the Ai4 campaign name
- medium fill-if-empty

**Result: 22 titles + 22 Campaign fields written, 0 errors.** No hard anomalies (no archived, no duplicate-campaign hazard). Effect: future same-campaign events now match these leads instead of hitting no-lead warns.

**One case flagged for review:** lead `75bbaf50-7477-11f0-8081-c56ae5e600e4` had old title "...Liam Loftus" but the Ai4 event resolved the person as "Person-58c91089" (the member_id / two-Lule collision class). Applied (reversible - old titles preserved in `wf1-release-evidence/item1-wrong-landing-APPLIED.json`), but worth confirming that person record is not a collision.

**Note on medium:** these 22 persons mostly already had medium `eMail`, so fill-if-empty correctly left them (NOT forced to LinkedIn). If Melisa wants medium normalized for these, that is a separate always-overwrite decision - not done here.

## 4. Post-ship item 2 - W1.0.11.1: person campaign field ALWAYS-OVERWRITE (Melisa)

The person **campaign** field (`fields.campaign` = 86157bb4..., "lh_campaign_name") changed from fill-if-empty to **ALWAYS-OVERWRITE**: every event writes the incoming `campaign.name` when it differs from the person's current value (same-campaign = idempotent, no redundant PATCH).

- **ONE-FIELD EXCEPTION** - only the person campaign field changes semantics. All other enrichment (company/position/li_url/public_id/member_id/location/medium/source) stays fill-if-empty. Person Create is unchanged (already sets campaign on create).
- **4 sites:** Person Patch Invited + M5 Person Patch Accepted (patch builders) and IF Rank Allows Invited + M5 IF Rank Accepted (gate fillable clauses).
- **Static 72/0** (discriminates 3 vs W1.0.11: R2, acceptance-correction, gate).
- **Fresh-double live check:** campaign A(sent) -> A; B(sent) -> flips to B; B again -> idempotent; C(accepted) -> flips to C; person not duplicated. 0 failures.
- **Deploy:** quiet window (26.5-min execution gap, no live traffic), tight deactivate->PUT->activate, DIFFS none.
