## Why one root cause explains all five (no second defect)
Person-level PATCHes never depend on `lead_id`, so stage worked. Every one of the five lead-bound writes depends on a `lead_id` that never came to exist because `Create Lead` threw. Sent branch: cold + channel + invite activity die with the throw. Accepted/reply branches: the F5 lead-id gates correctly divert to the warns because the lead legitimately isn't there. **Single root cause: `Create Lead` invalid-JSON on null `organization_id`.**

## Proposed fix (do NOT implement — same as E1's F13)
Make `Create Lead` null-safe on `organization_id` (and `person_id`): either `"organization_id": {{ JSON.stringify($('PID Resolved').item.json.organization_id ?? null) }}` (renders valid `null`), or move the body into a Code node that omits `org_id` when absent (matching the `Person Create` / `M6 Build` idiom). One fix restores the whole chain: lead created with cold+channel → accepted finds it (connected) → reply finds it (responded + reply activity + task).

## Why canary/live-suite missed it, and the regression test to add
Every test fixture (Person-5e07d3f5, T1, HR Test) had a **non-empty `company_name`** → `Org Search/Create` → `organization_id` non-null → `Create Lead` body valid. **Real organic leads frequently have no company** (Lule had none) → null org → invalid JSON. The fixtures' shape didn't match the real tenant case.
Add:
1. **Static:** render `Create Lead` `jsonBody` with `organization_id=null` and assert it is **valid JSON** with `organization_id` null/omitted (and `label_ids`/`channel`/`channel_id` present).
2. **Live-suite:** a `connection_request_sent` fixture with **empty `company_name`**; assert lead created (no error) with `cold` + channel `578`; then accepted + reply on that person assert `connected`→`responded`, invite/reply activities, and the transition task.
