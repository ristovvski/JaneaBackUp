## 2. Sent execution (9951)

- Chain ran: `… IF Company → Org None (no company) → IF Email Present → Person Search URL → IF URL Found(false) → Person Create → PID Resolved → Lead Search → Lead Create Gate → Create Lead`.
- `Person Create` **succeeded** → person **81603** (stage Invited).
- `Org None` ran (company empty) → **`PID Resolved.organization_id = null`**.
- **`Create Lead` ran and ERRORED**: `"JSON parameter needs to be valid JSON"` (node error; status=error).
- **label_ids in POST body:** intended `["a6d359b0-…"]` (`cold`) — but the body never sent because it was invalid JSON. **No response, no lead id.** `cold` was therefore never applied.

Root cause — the `Create Lead` `jsonBody` inlines `organization_id` as a bare expression with no `JSON.stringify`/guard:
```
"organization_id": {{ $('PID Resolved').item.json.organization_id }},
```
When there is no organization (empty company → `Org None` → `organization_id = null`), n8n renders `{{ null }}` as an **empty string**, producing:
```
"organization_id": ,      → invalid JSON → node throws before the HTTP call
```
(Verified by re-rendering the deployed template with the 9951 values: `json.loads` fails at the `organization_id` line. `person_id` is safe only because it is always numeric; `title`, `label_ids`, `channel_id` use `JSON.stringify`.)

## 3. Reply execution (9956)

- `M7 Lead Get` = `GET /v1/leads?person_id=81603` → **empty** (`success:true, data:[]`) — the lead genuinely doesn't exist.
- Path taken: `M7 Build → M7 IF Patch → M7 Person Patch (stage→Replied to invite) → M7 Labels Compute → M7 IF Lead ID(**false**) → **M7 No Lead Warn**`. **`M7 Lead Patch` did NOT run** (correctly gated off — there was no lead to patch). So `responded` was never applied because there was no lead.

This is the **F5/F10 guard working as intended**: person resolved but no lead → skip the lead write, fire the no-lead warn. The bug is entirely upstream (no lead was ever created).

## 6. Verdict + proposed fix (NOT implemented)

**(c) — the lead was never created by the sent branch.** `Create Lead` threw "JSON parameter needs to be valid JSON" because `organization_id` was `null` (no company) and the template inlines it without `JSON.stringify`/guard, yielding `"organization_id": ,`. Every downstream branch (accepted → M5 Slack Warn; reply → M7 No Lead Warn) correctly detected the missing lead and warned — they are not at fault. WF-ERR alerted the original error (9952).

Why the canary missed it: the Person-5e07d3f5 / T1 test leads all had a company (`Test Company Name`) → `organization_id` non-null → valid JSON. The **empty-company** path (common for real LinkedIn leads) was never exercised.

**Proposed fix (for approval — do not deploy yet):**
1. **Primary:** make `Create Lead` null-safe on `organization_id`. Either inline `"organization_id": {{ JSON.stringify($('PID Resolved').item.json.organization_id ?? null) }}` (renders valid `null`), or — matching the existing `Person Create`/`M6 Build` idiom — move the body into a Code node that builds the object and **omits `organization_id` when absent**, then `JSON.stringify`. Guard `person_id` the same way for robustness.
2. **Coverage:** add a static fixture + test for the empty-company sent case (no `Org`), asserting `Create Lead` body is valid JSON with `organization_id` omitted/null; add an empty-company case to the live suite.
3. **Recovery for this lead (81603):** after the fix, either replay the `connection_request_sent` for Lule (idempotent — person already exists, would create the missing lead + `cold`, then a reply replay would apply `responded`), or have an admin create the HeyReach lead and set `responded` manually. To decide with you.
