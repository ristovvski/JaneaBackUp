# dnc_pre_add_gate v2 — убрать sub-workflow fan-out, сделать per-row реально безопасным

Дата: 2026-08-26
Запрос (пришёл поверх concurrency-guard'а из того же дня): Nik решил, что Clay-прямой per-row
HTTP должен быть ПОДДЕРЖИВАЕМЫМ путём (table → n8n → verdicts back), а не запрещённым. Значит
чинить форму, а не звонящего: убрать per-row sub-workflow fan-out (реальный memory/exec
multiplier), не ограничивать вызовы.

## Done
- Прочитан реальный код `DNC__CheckLedger__v1` (`build_dnc.py:684-727`) перед тем как инлайнить —
  не передумывать логику заново, скопировать один-в-один (strongest-entry_type-wins, amendment 2).
- Проверен реальный размер реестра ДО выбора формы: **32 978 строк / ~28 МБ JSON** — bulk-load
  всей таблицы на каждый запрос был бы сам по себе тяжёлым; отсюда — точечные lookup'ы, не
  full-table read.
- Живой пробник (`zz_probe_datatable_multi_item.py`): dataTable `get`, накормленный 3 разными
  input-items с разными expression-значениями keyValue, реально гоняет lookup **по каждому item
  отдельно** и корректно коррелируется по СОБСТВЕННОМУ значению найденной строки (не по позиции/
  pairedItem) — подтверждено ДО того, как это легло в прод, не предположение.
- Новый граф `dnc_pre_add_gate` (13 нод, было 6→14→13): `Webhook → Mark Start → Build Items →
  Cap Check → [over-cap: 413] / Normalize Batch → (Get by LinkedIn, Get by Email параллельно) →
  Merge → Classify Batch → Build Report → Respond`. **Ноль executeWorkflow-вызовов.**
- Concurrency-guard из предыдущего инцидента (dnc_gate_concurrency, reject-429) **удалён**, не
  оставлен мёртвым кодом — он решал проблему, которую этот редизайн убирает в корне.
- Ответ вычищен от внутренних полей (`over_cap/norm/li_key/em_key`) перед выдачей — поймано живым
  тестом ДО отчёта (первая проверка после деплоя вернула их наружу).
- Self-reported `duration_ms`/`row_count` в ответе → пробросил в heartbeat монитора (avg/max
  latency за день) — «видеть headroom, не гадать».
- **Реальные пороги, измерено, не предположено:**
  - batch 200 строк в одном вызове → 200 OK, ~9.8с, счётчики верны.
  - per-row burst 10 конкурентно → 10/10 OK.
  - per-row burst 50 конкурентно → 50/50 OK.
  - per-row burst **100** конкурентно → **все 502, 15 execution'ов crashed, гейт снова
    auto-deactivated**. Инстанс-wide 503 держался ~45с.
  - per-row burst 200 → все 502 (гейт САМ не упал в краш-цикл на этот раз, но фронт отверг всё).
  - **Вывод: заявление «n8n держит 20 конкурентных нативно, просто очередь+drain» на практике НЕ
    подтвердилось на этом инстансе — потолок реально лежит между 50 и 100 одновременных
    соединений**, независимо от того, что сама execution теперь дешёвая.
- Реактивирован дважды за сессию (после 100-burst'а), фикстура Barry/Dennis проверена и после
  первого редеплоя, и после финального — оба раза верно.
- 94/94 статических теста проходят (переписаны 2 теста под новый граф, старые ссылались на
  удалённые ноды `Call CheckLedger`/`Classify Row`).

## Дополнение: реальный баг найден через CSV Стефана (тот же день)

Nik скинул реальный Clay-экспорт (`Speakers-and-Attendees-Enrichment-NEW-Import-View-export...
csv`, 211 строк, `HTTP API`/`Gate Result`/`Reason` — колонки Стефана). Разобрал:
- 15 из 211 строк реально стрельнули (`HTTP API = Status Code: 200`), 196 ещё не запускались.
- Из 15 успешных — **только 1** (единственная, которая была BLOCKED) получила заполненные
  `Gate Result`/`Reason` в Clay. Остальные **14 (все CLEAN) — 200 OK, но колонки пустые**.
- Причина: ответ гейта бакетизирован (`clean[]/blocked[]/unresolvable[]/rows[]`), плоского поля
  на верхнем уровне не было вообще — что бы Clay ни маппил (похоже на `blocked[0].reason`),
  оно существует только когда строка реально BLOCKED.
- Фикс: `gate_report_js` — при **ровно одной** входной строке (это и есть Clay per-row кейс)
  добавляет `gate_result/reason/registry_row_ref/identity_key` НА ВЕРХНИЙ уровень ответа, поверх
  существующей структуры (batch не тронут — при 2+ строках верхнеуровневых полей НЕТ, чтобы не
  давать ложно-однозначный ответ на многострочный вызов).
- Живая проверка: тот самый `pii-39036e6d@example.invalid` (был пустой в CSV) → теперь
  `gate_result: "CLEAN"` на верхнем уровне; фикстура Barry/Dennis (BLOCKED) — тоже верно; batch
  из 2 строк — верхнеуровневых полей нет, `counts` как раньше.
- Тест добавлен (95-й), редеплой `versionId c5eb6a6a`, гейт стабилен.
- **Nik/Стефану нужно поправить маппинг колонки в Clay** — с чего бы он ни читал сейчас
  (`blocked[0].reason`?), переключить на плоские `gate_result`/`reason` с верхнего уровня ответа.
  Это Clay-сторонняя правка, руками сделать не могу (нет проверенного API на формулы колонок).
