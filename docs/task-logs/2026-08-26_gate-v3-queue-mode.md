## Done
- Новый граф гейта: `Webhook → Is Retrieve? → [retrieval branch] / [Mark Start → ... → Check Queue
  Depth → Decide Sync Or Queue → Is Sync? → [sync path] / [Enqueue Rows → 202]]`.
- Новый воркфлоу `dnc_gate_queue_drainer` — schedule раз в 2 мин, батч 50, интервал тика = сам
  breather (без Wait-ноды). **Переиспользует `gate_classify_batch_js` дословно** (тот же jsCode
  и в гейте, и в дрейнере — тест на побайтовое совпадение) — никакого дрейфа логики.
- `dnc_pre_add_gate_monitor` расширен: глубина очереди на каждый 15-мин тик, детект "застрял"
  (4 замера подряд, глубина не падает — окно ~1ч, специально шире принятых 30 мин, чтобы не
  кричать на обычный ещё-drain'ящийся burst), алерт один раз за эпизод, heartbeat строка.
- **Два реальных бага пойманы ЖИВЬЁМ до того, как дошли до Стефана**:
  1. `Check Queue Depth` не был fail-open → сломал бы ЛЮБОЙ вызов гейта (даже синхронный) в
     момент деплоя, пока `dnc_gate_queue` не создана. Пофикшено ДО деплоя в прод.
  2. **Настоящий баг найден на реальном фикстур-вызове**: Dennis (known-blocked) вернулся CLEAN.
     Причина — `Merge("append", 2 inputs)`, питаемый ДВУМЯ параллельными lookup-нодами
     (LinkedIn/Email), НЕ дожидается обоих входов в этом графе — стреляет ПО ПРИХОДУ каждой
     ветки отдельно, `Classify Batch` запускался ДВАЖДЫ с частичными данными (первый раз —
     только пустой LinkedIn-результат → оба CLEAN; второй — реальный Email-матч, но ответ уже
     ушёл с первого прогона). Живой пробник подтвердил: ОДИН lookup с `matchType:anyCondition` и
     ДВУМЯ условиями (linkedin_url_norm OR email_lc) работает корректно, без Merge вообще.
     Переписан гейт И дрейнер на этот единый lookup (`dt_get_or2`, новый переиспользуемый
     хелпер) — Merge-барьер устранён полностью, не просто обойдён.
  3. При первом фиксе fail-open обнаружился ТРЕТИЙ баг: n8n's dataTable error-выход НЕ
     единообразен — иногда `{error:"..."}`, иногда (эта нода, эта ошибка) просто ЭХОИТ исходные
     input-элементы без всякого маркера ошибки. Фильтр по `!r.error` не ловил это молча.
     Исправлено на позитивную проверку (реальная queue-строка обязана нести `row_key`+`status`).

  результат" (позитивно), а не "есть ли поле error" (негативно).
